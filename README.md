Travlr Getaways — Full Stack Web Application
CS-465 Full Stack Development I - Southern New Hampshire
Travlr Getaways is a full stack travel booking application built on the MEAN stack (MongoDB, Express, Angular, Node.js). It has two sides:

Customer site – a server-rendered Express/Handlebars website where travelers browse available trips.
Admin site – an Angular single-page application (SPA) where authenticated administrators add, edit, and manage trips.

Both sides are powered by a shared RESTful API backed by a MongoDB database, and the admin side is protected with JWT-based authentication.

Tech Stack
Layer	Technology
Database	MongoDB with Mongoose ODM
Backend / API	Node.js, Express
Customer frontend	Express + Handlebars (HBS) templates
Admin frontend	Angular SPA
Authentication	Passport (local strategy), JSON Web Tokens, hashed + salted passwords
Testing	Postman, browser dev tools
Architecture

Compare and contrast the types of frontend development used in the project.

The project used three distinct approaches to the frontend, and moving through them in order made the trade-offs very clear.

The customer site started as static HTML served by Express. That was simple and fast to stand up, but every page was hardcoded — adding a trip meant editing markup by hand, and the header and footer were duplicated across every file. Refactoring to Express with Handlebars templates fixed most of that. Pages became templates with partials for shared pieces like the header and footer, and the trip listings were generated by looping over data instead of being written out by hand. The server still does the rendering, so each navigation is a full page request, but the content became data-driven.

JavaScript was the glue throughout: Node and Express on the server, the controllers that call the API and pass data to the views, and later TypeScript in Angular.

The admin side was built as an Angular single-page application. Instead of the server sending a new HTML page for each action, the browser loads the application once and Angular swaps components in and out on the client, pulling data from the REST API as needed. That makes the admin experience much more responsive and app-like, and it cleanly separates the presentation layer from the backend. The trade-off is more upfront complexity — components, services, routing, and state all live in the browser — and SPAs need extra work if search engine visibility matters. That's exactly why the split made sense here: the public customer site benefits from simple server-rendered pages, while the admin tool benefits from the interactivity of an SPA.

Why did the backend use a NoSQL MongoDB database?

MongoDB stores data as JSON-like documents, which lines up naturally with a JavaScript stack: a trip document in the database looks almost exactly like the object Express returns and the object Angular displays, so there's very little translation between layers. MongoDB is also schema-flexible, which helped during iterative development when fields changed from module to module. Mongoose added just enough structure on top — schemas, validation, and model methods — to keep the data consistent without the rigidity of a relational schema. MongoDB also scales horizontally well, which suits a web application that could grow over time.

Functionality

How is JSON different from JavaScript, and how does JSON tie the frontend and backend together?

JavaScript is a full programming language with variables, functions, logic, and behavior. JSON (JavaScript Object Notation) is only a data format. It borrows JavaScript's object syntax but is stricter: keys must be double-quoted strings, and it can only hold data — strings, numbers, booleans, arrays, objects, and null. It can't contain functions or executable code. Because of that, JSON is language-independent and safe to send across a network.

In this project, JSON was the common language between every layer. Early on, trip data lived in a static JSON file that the Express views read from. Later, the Express API queried MongoDB and returned trips as JSON responses. The Handlebars customer site consumed that JSON to render pages, and the Angular admin site sent and received JSON through its services when listing, adding, and editing trips. Even the authentication token came back from the login endpoint inside a JSON response. Having one consistent format meant the frontend and backend could be developed and tested independently, as long as both agreed on the shape of the data.

Instances of refactoring to improve functionality and efficiency, and the benefits of reusable UI components.

Static HTML → Handlebars templates. Hardcoded pages were converted to templates with shared partials, eliminating duplicated markup and making pages data-driven.
Hardcoded data → JSON file → MongoDB API. Trip data moved from markup, to a JSON file, to a database served through REST endpoints. Each step made the data easier to change without touching the views.
Routes separated from controllers. Route definitions were kept thin and the logic was moved into controller files, which made the code easier to read, test, and extend.
Angular services. API calls were centralized in a trip-data service and authentication logic in an authentication service, so components didn't each make their own HTTP calls.
HTTP interceptor. Rather than manually attaching the JWT to every request, an interceptor added the authorization header automatically.

The clearest example of a reusable UI component was the Angular trip card. One component defines how a single trip is displayed, and the trip listing simply renders it for every trip in the data. The benefits are consistency (every trip looks the same), maintainability (a design change is made in one place), less code overall, and easier testing because each component has a single, focused responsibility. The add-trip and edit-trip forms followed the same idea of small, purpose-built components that could be composed together.

Testing

Explain your understanding of methods, endpoints, and security in a full stack application.

An endpoint is a specific URL the API exposes, such as /api/trips or /api/trips/:tripCode. An HTTP method defines what action is performed at that endpoint:

Method	Purpose	Example
GET	Retrieve data	GET /api/trips – list all trips
GET	Retrieve one record	GET /api/trips/:tripCode – a single trip
POST	Create data	POST /api/trips – add a trip
PUT	Update data	PUT /api/trips/:tripCode – edit a trip
POST	Authenticate	POST /api/login, POST /api/register

Each combination of method and endpoint needs its own testing. I used Postman to send requests directly to the API and confirm the status codes, response bodies, and database changes were correct before connecting the Angular frontend — that way, if something broke, I knew whether the problem was in the API or the UI. Testing covered the expected paths (valid requests return 200/201 and the right data) as well as failure cases (missing fields, invalid trip codes, malformed JSON).

Security added another layer to testing. Read-only GET requests for the customer site stayed public, but the routes that modify data (POST and PUT) were protected so only an authenticated admin could use them. Passwords are never stored in plain text — they are salted and hashed. When an admin logs in, the server verifies the credentials and returns a signed JSON Web Token. The Angular app stores that token and sends it in the Authorization header on protected requests, and the backend validates it before allowing the change.

That made testing harder in a few ways: a protected endpoint has to be tested both without a token (it should reject the request with a 401 Unauthorized) and with a valid token (it should succeed). In Postman, that meant first calling the login endpoint, copying the token, and adding it as a Bearer token on later requests. Expired or malformed tokens, missing secrets in the environment configuration, and making sure the frontend actually attached the header were all new failure points to account for. The takeaway is that security can't be bolted on and assumed to work — it has to be tested as deliberately as the features themselves.

Running the Project Locally
Install Node.js and MongoDB.
Clone the repository and install dependencies in both the root and the Angular admin folder:
bash
   npm install
   cd app_admin && npm install
Create a .env file in the project root with your JWT secret:
   JWT_SECRET=your_secret_here
Start MongoDB, then start the Express server from the project root:
bash
   npm start

The customer site runs at http://localhost:3000. 5. Start the Angular admin app:

bash
   cd app_admin
   ng serve

The admin site runs at http://localhost:4200.
